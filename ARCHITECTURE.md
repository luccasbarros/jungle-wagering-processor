# Architecture

## Overview

One use case, `SubmitWagerTransaction`, serves both entry points. HTTP and the SQS consumer parse their own envelope, then hand the same command to it. Everything that must be atomic happens in one PostgreSQL transaction; the only things outside it are the fast-path replay read before it and the publish of already-committed outbox rows after it.

```
 HTTP POST /wagering/transactions            SQS wager-transactions.fifo
 (Idempotency-Key header)                    (envelope.messageId, data.idempotencyKey)
            |                                             |
            v                                             v
   WageringController                              SqsConsumer (per instance, opt-in)
            |                                             |  parse -> permanent error? -> DLQ + ack
            +---------------------+-----------------------+
                                  v
                    SubmitWagerTransaction.execute(command, inbox?)
                                  |
          fast path: SELECT by idempotency_key -> replay (same result, idempotentReplay=true) or 409
                                  |
     +----------------------------v-----------------------------------------------+
     | BEGIN; SET LOCAL lock_timeout = '3s'                                       |
     |  1. INSERT inbox_messages (queue path only; PK = consumer + messageId)     |
     |  2. INSERT wager_transactions ... status = PENDING   (insert-first:        |
     |     unique violation -> ROLLBACK -> replay or 409, no lock ever taken)     |
     |  3. SELECT wallet FOR NO KEY UPDATE   (LOSS reads without a lock)          |
     |  4. resolve reference (providerId, referenceExternalTransactionId),        |
     |     check "already reversed", WagerTransaction.applyTo(wallet) -> decision |
     |  5. INSERT wallet_ledger_entries (at most one per transaction and wallet)  |
     |     UPDATE wallets SET balance, version+1 WHERE id = ? AND version = ?     |
     |  6. UPDATE wager_transactions: status, failure_code, observed_balance      |
     |  7. INSERT outbox_messages (Processed | Rejected | PendingReference,       |
     |     plus WalletBalanceChanged when the balance moved)                      |
     | COMMIT                                                                     |
     +----------------------------+-----------------------------------------------+
                                  |
            HTTP: 200 / 422 / 202 from the stored status   SQS: DeleteMessage (ack) only now
                                  |
      +---------------------------+------------------------------+
      v                                                          v
 OutboxPublisherLoop (every instance)                PendingReferenceWorker (every instance, 2 s tick)
   claim earliest pending event per wallet             claim one PENDING_REFERENCE row due now
   FOR UPDATE SKIP LOCKED, publish to                  FOR NO KEY UPDATE SKIP LOCKED, lock wallet,
   wager-events.fifo (group = walletId,                re-run applyTo; exhausted -> REJECTED
   dedup id = eventId), mark published,                REFERENCE_NOT_FOUND; else backoff 2^n x 2 s,
   or scheduleRetry (2 s, 4 s ... 5 min cap)           cap 5 min, 12 attempts or 24 h
```

Layers: `domain/` (no framework imports, factories + `rehydrate`, every rule in `WagerTransaction.applyTo` and `Wallet`), `application/` (use cases, ports `UnitOfWork`, `Clock`, `IdGenerator`, `EventPublisher`, `Metrics`, hand-written input parsing), `infrastructure/` (MikroORM unit of work and `EntitySchema`s, migration, SQS, workers, pino, prom-client), `interface/http/` (controllers, one status table, error filter, no-op `AuthGuard`).

## Decisions

| Decision | Alternatives | Why | Limits |
|---|---|---|---|
| **MikroORM 7** with `EntitySchema` mapping and immediate EntityManager operations (`em.insert`, `em.nativeUpdate`, `em.execute`) inside `em.fork().transactional()`; no deferred Unit of Work flush on the money path. Chosen after a one-hour spike (`spike/orm-spike.ts`) that proved `transactional` + lock modes under Bun | TypeORM; raw SQL for everything; `persist` + `flush` | The spec prefers MikroORM; `EntitySchema` keeps the domain free of decorators; statement order is the concurrency argument (insert-first, then lock) and a deferred flush may reorder statements and hides where a unique violation fires | Identity Map and change tracking are barely used; the ORM is the mapper and the transaction boundary here |
| **Money** = domain class over `decimal.js` with a private `Decimal.clone({ precision: 40 })`, decimal string in and out, exactly 2 decimals, amounts capped at 17 integer digits (the `NUMERIC(19,2)` range) on input and on every result; persisted as `NUMERIC(19,2)` + `CHAR(3)` in separate columns, read back as strings (MikroORM `decimal` type) and rehydrated through `Money.from` | Integer cents in `BIGINT`; unbounded `Decimal`; global `Decimal` config | Strings and `NUMERIC` never pass through a float; the cap fails fast in the domain instead of at insert time; a private clone cannot be reconfigured by another module | Domain width is coupled to the column width; widen both together |
| Currency must match `^[A-Z]{3}$`, no lowercase normalization; `equals` across currencies is `false`, `add`/`subtract`/`isLessThan` across currencies throw; `Money.from` refuses negatives (negatives exist only as results of `negate`/`subtract`) | Uppercase on input; ISO-4217 list; signed factory | One accepted form means no false idempotency conflicts; equality has an answer across currencies, arithmetic does not; input contracts never carry negatives, reconciliation still needs a negative `difference` | Syntactically valid but nonexistent codes (`XYZ`) are accepted |
| **Transaction strategy**: pessimistic row lock `SELECT ... FOR NO KEY UPDATE` on the wallet (raw SQL via `em.execute`), plus `UPDATE wallets ... WHERE version = ?` as a second guard (0 rows = 503) | `LockMode.PESSIMISTIC_WRITE` (`FOR UPDATE`); optimistic locking with retry; lock before insert | With insert-first, the transaction row's FK check holds `FOR KEY SHARE` on the wallet, and `FOR UPDATE` conflicts with it: two concurrent bets deadlock (`40P01`), measured with a two-connection script before coding. `FOR NO KEY UPDATE` still excludes every other writer. Locking before the insert would keep `FOR UPDATE` but duplicates would then queue on a hot wallet's lock. The version guard turns a forgotten lock into a 503 instead of a lost update (mutation M1) | MikroORM has no lock mode for it, so this one statement is raw SQL; no automatic retry on 503, the provider resends |
| `SET LOCAL lock_timeout = '3s'` on every money transaction; `55P03`, `40P01`, `40001` become `LockConflictError` (503 + `Retry-After: 1`, counted in `lock_conflicts_total{reason}`) | Wait indefinitely; shorter timeout | A hot wallet must not pile up connections; 3 s covers a normal transaction many times over | A wallet held longer than 3 s by anything turns requests into 503s |
| **Idempotency**: insert the `wager_transactions` row in `PENDING` as the first money statement (insert-first), before any lock; `uq_wager_transactions_idempotency_key` is the arbiter. Unique violation -> rollback -> fetch the winner -> replay if `payloadHash` matches, else 409 | Lock then check; `SELECT` before insert; in-memory cache | A duplicate never enters the wallet lock queue nor runs a domain rule; the unique index decides a 50-way race in one place. The fast-path `SELECT` before the transaction only saves work, the index is the guarantee | The surviving mutant "insert later" shows the index, not the insert position, is what protects money; insert-first is a throughput choice |
| Idempotency key is **globally unique**; `(provider_id, external_transaction_id)` is unique too; an external id reused under a different key answers 409 `IDEMPOTENCY_CONFLICT` with nothing stored | Key scoped per provider; replay when the hash matches; a dedicated code | Spec 9: the header is the source of truth; with the recommended `{providerId}:{externalTransactionId}` format providers cannot collide; disagreement between key and external id is a provider bug, not a replay | Reuses `IDEMPOTENCY_CONFLICT` instead of a dedicated code |
| `payloadHash` = SHA-256 hex of a canonical JSON (keys sorted recursively by UTF-16 code unit, no whitespace, `undefined` dropped, `null` reference treated as absent) of the 9 business fields: `providerId`, `externalTransactionId`, `playerId`, `walletId`, `roundId`, `gameId`, `kind`, `money {amount, currency}`, `referenceExternalTransactionId` | Full RFC 8785 JCS; hash of the raw body | No numbers among the fields (money is a validated string), so JCS number rules never apply; header, correlation id and transport envelope stay out, so a resend with a different `X-Correlation-Id` is still a replay | Arrays keep order; only the wager fields are covered by a fixed schema |
| Observed balance snapshot stored on the transaction row (`observed_balance`, `observed_balance_currency`), set atomically with the decision; replay and GET answer from it | Join `wallets` on read | Spec rule 7: a replay returns the balance seen then, even after later movements; a `CURRENCY_MISMATCH` transaction is stored in its own currency but observed the wallet's, so the row must say which currency its snapshot is in | One more column pair |
| **HTTP status is a pure function of the stored status**: PROCESSED 200, REJECTED 422, FAILED 422, PENDING_REFERENCE 202; `httpStatusFor` throws on PENDING (never leaves the use case) | 201 for created; 500 for FAILED; `Partial` table with `?? 500` | A replay must answer exactly what the original did; FAILED is terminal like REJECTED and carries its code, a 5xx would tell the provider to resend forever; an exhaustive `Record` makes a new status a compile error instead of a silent 500 | 422 for FAILED reads as "fix the payload" to a provider that ignores `failureCode`; the taxonomy says it means operator intervention |
| Error body `{ failureCode, message }` on every endpoint, Nest's own 400 for malformed JSON remapped to `INVALID_PAYLOAD`, 503 adds `Retry-After: 1` | Nest default error shape | One contract: the provider never parses a message | Unknown errors answer 500 without a `failureCode` |
| Driver errors translated in the persistence adapter **by constraint name and SQLSTATE**: idempotency key -> replay, provider+external id -> 409, inbox PK -> `DuplicateInboxMessageError`, player+currency -> 409, wallet FK -> 404; `57P0x`, `53300`, class `08`, socket errors -> 503 | Parse messages; pre-check `SELECT`s | Every constraint has an explicit name (`pk_`, `uq_`, `ck_`, `fk_`, `ix_`) for exactly this; the FK makes "wallet exists" a database fact with zero extra queries | A `23505` on `uq_one_reversal_per_reference` is not translated (500): it can only fire if the wallet lock is bypassed |

## Model and schema

Domain classes follow the spec's shape: private constructors, `create`/`open`/`enqueue`/`receive` factories that validate, `rehydrate` that only rebuilds. `WalletLedgerEntry` is frozen (`Object.freeze`) and has no transition methods; `Wallet.debit`/`credit` return the matching entry so balance and ledger cannot drift apart in code. `version` starts at 1 and bumps only when the balance moves (LOSS and REJECTED leave it alone).

Schema (`src/infrastructure/persistence/migrations/Migration20261109000000InitialSchema.ts`, one reversible migration):

- `wallets`: `UNIQUE (player_id, currency)`, `CHECK (balance >= 0)`, `CHECK (version >= 1)`, currency format CHECK.
- `wager_transactions`: `UNIQUE (idempotency_key)`, `UNIQUE (provider_id, external_transaction_id)`, `UNIQUE (id, wallet_id, currency)` (target of the ledger FK), FK to `wallets`, self FK `reference_transaction_id`, CHECKs on `kind`, `status`, `amount >= 0`, currency format, reversal-has-reference, failure-code-iff-terminal-failure, observed-balance-has-currency, `retry_attempts >= 0`; partial unique index `uq_one_reversal_per_reference`; partial index `ix_pending_reference (next_retry_at) WHERE status = 'PENDING_REFERENCE'`.
- `wallet_ledger_entries`: `seq BIGSERIAL UNIQUE`, FK to `wallets`, composite FK `(transaction_id, wallet_id, currency)`, `UNIQUE (transaction_id, wallet_id)`, `amount > 0`, `balance_before >= 0`, `balance_after >= 0`, `ck_ledger_balanced`, direction CHECK, currency format CHECK, `ix_ledger_wallet_seq (wallet_id, seq)`; triggers `trg_ledger_immutable` (UPDATE/DELETE) and `trg_ledger_no_truncate`.
- `inbox_messages`: `PRIMARY KEY (consumer_name, message_id)`.
- `outbox_messages`: `attempts >= 0`, partial indexes `ix_outbox_due (next_attempt_at, occurred_at)` and `ix_outbox_pending_by_aggregate (aggregate_id, occurred_at)`, both `WHERE published_at IS NULL`.

The schema-constraints suite asserts, for each forbidden write, the exact constraint or trigger name that refused it.

## Concurrency

The unit of concurrency is the wallet row. Every balance change happens with `SELECT ... FOR NO KEY UPDATE` held on that row inside the same transaction that reads the balance, writes the ledger entry and updates the balance with `WHERE version = ?`. There is no global lock: a test holds one wallet locked while bets on another wallet are served. Workers (outbox, pending reference) coordinate through `SKIP LOCKED` claims, so any number of instances can run them. The lock flavour matters: see the transaction-strategy decision for the measured `FOR UPDATE` deadlock against the FK's `KEY SHARE`.

Defence in depth, in one sentence: the lock gives the right business answer (REJECTED), the version guard turns a forgotten lock into a 503 instead of wrong money, `CHECK (balance >= 0)` blocks a negative balance, and the test invariant `balance == SUM(ledger)` catches whatever would pass all three.

Shutdown order (Nest 12, `stop_grace_period: 30s`): `beforeApplicationShutdown` drains the consumer (current poll up to 20 s, then the message in flight, bounded by `lock_timeout`), finishes the outbox batch and the worker tick; only then `onApplicationShutdown` closes the ORM and HTTP stops. A replica keeps answering HTTP almost until the end of its stop, which is why a graceful `docker compose restart` of all replicas produced zero client-visible errors in the e2e run.

## Idempotency

Persistent only: the `wager_transactions` row is the record, the unique index is the arbiter, the fast-path read is an optimisation. A replay returns the stored status, `transactionId`, `failureCode` and the balance observed at the decision, with `idempotentReplay: true`. A replay of a transaction that answered 202 and has since been decided answers the decided status. Same key, different `payloadHash` is 409. The queue path adds the inbox: the same `messageId` is a duplicate (`duplicates_detected_total{detector="inbox"}`), a new `messageId` carrying an already processed operation is a replay by key (`detector="idempotency_key"`); both are acked, neither moves money.

## Messaging and failures

- Ack (`DeleteMessage`, one call site) happens only after the use case returns, which is after `COMMIT`. Mutation "ack before handle" is caught by the retry test.
- Business refusals are committed REJECTED rows and acked. Transient failures (lock timeout, deadlock, connection, version conflict) are retried through `ChangeMessageVisibility` with 2, 4, 8, 16 s; the 5th delivery goes to the DLQ with `TRANSIENT_FAILURE`. Permanent failures (unparsable envelope, unknown wallet, OPENING, invalid money) go to the DLQ at once with the original body and the reason as message attributes.
- Outbox: events are rows written in the money transaction; a publisher that dies between `SendMessage` and `COMMIT` leaves the row pending, another instance republishes with the same `eventId` as `MessageDeduplicationId`, and the consumer dedups by `eventId`. Tested with a real rollback after a real publish.
- Pending references: `REFUND`, `ROLLBACK` (and a `WIN`/`LOSS` with a reference) whose reference is missing are stored as `PENDING_REFERENCE` (202 on HTTP, `WagerTransactionPendingReference` event) and re-applied by the worker under the same wallet lock and the same rules; exhaustion ends `REJECTED REFERENCE_NOT_FOUND` with a `WagerTransactionRejected` event.
- FIFO is an optimisation, not the guarantee: the e2e test publishes the same message three times under three different `MessageGroupId`s so three replicas receive it simultaneously; only the inbox PK stops the copies.

## Failure taxonomy and HTTP status mapping

Rule for the provider: 4xx means do not resend as-is, decide from `failureCode`; 503 means resend the same request; 202 means wait, the result will come through the events or a replay.

| HTTP | When | `failureCode` | Stored? |
|---|---|---|---|
| 201 | Wallet created | | yes |
| 200 | Transaction PROCESSED, or replay of one; GETs | | yes |
| 202 | PENDING_REFERENCE (reference not yet arrived), or replay while still pending | | yes |
| 422 | REJECTED by a business rule, or replay of one | `INSUFFICIENT_FUNDS`, `REVERSAL_WOULD_OVERDRAW`, `CURRENCY_MISMATCH`, `WALLET_PLAYER_MISMATCH`, `REFERENCE_NOT_FOUND`, `REFERENCE_KIND_NOT_ALLOWED`, `REFERENCE_SCOPE_MISMATCH`, `REFERENCE_NOT_PROCESSED`, `REFERENCE_ALREADY_REVERSED`, `AMOUNT_MISMATCH` | yes, auditable, no ledger, no version bump |
| 422 | FAILED (infrastructure dead end reached by the worker), or replay of one | `PERMANENT_FAILURE` | yes |
| 400 | Payload or header problem | `INVALID_PAYLOAD`, `INVALID_MONEY`, `INVALID_CURSOR`, `MISSING_IDEMPOTENCY_KEY`, `KIND_NOT_SUBMITTABLE` | no |
| 404 | Unknown resource | `WALLET_NOT_FOUND`, `TRANSACTION_NOT_FOUND` | no |
| 409 | Same key with a different payload; external id under another key; duplicate wallet | `IDEMPOTENCY_CONFLICT`, `WALLET_ALREADY_EXISTS` | no |
| 503 + `Retry-After: 1` | Lock timeout, deadlock, serialization, version conflict, connection loss | `TRANSIENT_FAILURE` | no |
| 500 | Programming error | none | no |

Failure codes by what the provider should do:

| Code | Meaning | Provider action |
|---|---|---|
| `INSUFFICIENT_FUNDS` | BET above the balance | Do not resend; the player cannot afford it |
| `REVERSAL_WOULD_OVERDRAW` | Undoing a WIN or a REFUND would go negative | Do not resend; operational case, distinct from a bet without funds |
| `CURRENCY_MISMATCH` | Transaction currency differs from the wallet's | Fix the payload or the wallet |
| `WALLET_PLAYER_MISMATCH` | Wallet belongs to another player | Fix the payload |
| `REFERENCE_NOT_FOUND` | Reference never arrived within 12 attempts / 24 h | Send the referenced operation, then a new reversal |
| `REFERENCE_KIND_NOT_ALLOWED` | REFUND of a non-BET; ROLLBACK of a LOSS/ROLLBACK | Fix the payload |
| `REFERENCE_SCOPE_MISMATCH` | Reference exists but in another player, wallet, currency or round | Fix the payload |
| `REFERENCE_NOT_PROCESSED` | Reference exists but is REJECTED or FAILED | Nothing to reverse |
| `REFERENCE_ALREADY_REVERSED` | Reference already has a PROCESSED reversal | Nothing to do |
| `AMOUNT_MISMATCH` | Reversal amount differs from the reference | Fix the amount (partial reversals are out of scope) |
| `INVALID_PAYLOAD`, `INVALID_MONEY`, `INVALID_CURSOR`, `MISSING_IDEMPOTENCY_KEY`, `KIND_NOT_SUBMITTABLE` | Request shape | Fix the request |
| `WALLET_NOT_FOUND`, `TRANSACTION_NOT_FOUND` | Unknown id | Check the id |
| `IDEMPOTENCY_CONFLICT`, `WALLET_ALREADY_EXISTS` | Collides with an existing record | Use a new key / look up the existing one |
| `TRANSIENT_FAILURE` | Our side, momentary | Resend the same request |
| `PERMANENT_FAILURE` | Our side, repeated unexpected errors while applying a pending reference | Do not resend; operator intervention |

## Spec interpretations

1. Rule 4 is read strictly: once a reference has a PROCESSED REFUND or ROLLBACK, any further reversal of either kind is refused with `REFERENCE_ALREADY_REVERSED` (partial unique index `uq_one_reversal_per_reference`, no `kind` in it); the letter of the rule would allow a ROLLBACK after a REFUND, but that would credit the BET twice.
2. A WIN or LOSS that carries `referenceExternalTransactionId` requires a PROCESSED BET of the same provider, player, wallet, currency and round; until it arrives the transaction waits as PENDING_REFERENCE and ends REJECTED `REFERENCE_NOT_FOUND` at the policy limit, so a WIN is never credited against a BET that never existed.
3. An `externalTransactionId` already stored under a different Idempotency-Key answers 409 `IDEMPOTENCY_CONFLICT` even when the payload is identical: the key is the source of truth and the external id is the provider's own uniqueness, so disagreement between them is a provider bug, not a replay.
4. The Idempotency-Key is unique globally (`uq_wager_transactions_idempotency_key`), not per provider; with the recommended `{providerId}:{externalTransactionId}` format two providers cannot collide.
5. A FAILED transaction (infrastructure dead end after the pending-reference policy is spent) emits no integration event; spec section 11 defines none, and the row stays auditable with `failureCode = PERMANENT_FAILURE`.
6. A replay of a transaction that answered 202 PENDING_REFERENCE and has since been decided answers the decided status (200 or 422) with the balance observed at the decision, not the original 202.
7. A replay of a FAILED transaction answers 422 with the stored result and `failureCode = PERMANENT_FAILURE`: terminal, do not resend; a 5xx would invite the provider to retry forever, and the body keeps the submission shape so the replay is the original result.
8. A reference that can never resolve is refused at submission with 400 `INVALID_PAYLOAD` (DLQ over SQS) instead of waiting out the TTL: a REFUND or ROLLBACK that references its own `externalTransactionId`, and a BET that carries `referenceExternalTransactionId` (the rules table gives BET nothing to reference).
9. Logs and DLQ `failureReason` attributes carry the error class name and its SQLSTATE/driver code, never the driver message, because Postgres echoes the failing statement with its parameters (amounts) inside it (spec section 12); our own `DomainError` messages contain no values and travel whole.
10. The outbox publisher claims one event per wallet per round (per-wallet order through `NOT EXISTS` on the earlier pending row) and polls again at once while a round claimed anything, pausing 500 ms only on an empty round; a burst on one wallet drains at about one SQS round trip per event (measured with 20 events: 10.05 s before, under 1.2 s after).
11. "Instance" in the concurrency and outbox suites is a Nest application with its own connection pool inside one Bun process; every mutual exclusion is Postgres-side (wallet row lock, `SKIP LOCKED` claims, unique indexes), so in-process applications and separate OS processes are equivalent for the argument. The e2e suite then runs three real containers behind nginx.
12. OPENING transactions are readable through `GET /providers/internal/wagering/transactions/opening:<walletId>`, kept on purpose as the audit trail of the initial credit; they can never be submitted (400 `KIND_NOT_SUBMITTABLE` on HTTP, DLQ on the queue).
13. If the consumer's explicit dead-letter send succeeds but the `DeleteMessage` after it fails, the broker's own redrive on the next delivery can place a second copy in the DLQ (different `MessageDeduplicationId`, no attributes); it has no financial effect and the operator sees the duplicate by `sourceMessageId`.

## Authentication

Not implemented, by the spec's own invitation (section 2): it scores nothing and would have competed with the money path in the timebox. The extension point is `src/interface/http/auth.guard.ts`, a no-op `CanActivate` registered as the global `APP_GUARD`, so every controller already runs behind a guard.

The design I would adopt: Keycloak in the compose as the Identity Provider, one OAuth2 client per game provider using the client-credentials grant (machine to machine, no users, no password table). The guard validates the bearer JWT offline against Keycloak's JWKS (RS256, issuer, audience, expiry), and a `ProviderIdentityPort` maps the token's client id (`azp`) to a `providerId`. The use case then checks that `payload.providerId` equals the authenticated provider, so provider A cannot submit or reverse operations in provider B's name; that is the one check that belongs in the domain, not the guard. `/health/*` and `/metrics` stay open (`@Public()` metadata read by the guard). Queue messages remain an internal trusted channel, as the spec allows, with the same domain validations on the `providerId` they carry. Token revocation would rely on short lifetimes (minutes) rather than introspection on every request.

## Observability

Structured JSON logs through pino. Every line carries the current log context: `correlationId` (from `X-Correlation-Id` or generated and echoed back in the response header; for queue messages the envelope `messageId`), `messageId`, `transactionId`, `walletId`, `providerId`, `kind`, `status`, `failureCode`. The context holds identifiers only; money keys are redacted as a second guard; error logs carry class name and SQLSTATE, not the driver message. The request line is written once per request at `info`.

Metrics on `GET /metrics` (Prometheus text format, one registry per instance):

| Metric | Type | Labels |
|---|---|---|
| `wager_transactions_total` | counter | `status` (decisions, not replays) |
| `duplicates_detected_total` | counter | `detector` = `idempotency_key` \| `inbox` |
| `retries_total` | counter | `kind` = `outbox_publish` \| `pending_reference` \| `message_redelivery` |
| `dlq_messages_total` | counter | messages the consumer sent to the DLQ |
| `dlq_depth_messages` | gauge | `ApproximateNumberOfMessages` of the DLQ at scrape time (`NaN` if SQS does not answer) |
| `pending_reference_exhausted_total` | counter | `status` the worker gave up into (`REJECTED` or `FAILED`) |
| `lock_conflicts_total` | counter | `reason` = `lock_timeout` \| `deadlock` \| `serialization` \| `version_conflict` |
| `outbox_lag_seconds` | gauge | age of the oldest unpublished event, read from Postgres at scrape time |
| `reconciliation_divergence_total` | counter | wallets whose balance did not match the ledger |
| `processing_duration_seconds` | histogram | submission latency, replays and errors included |

Health: `GET /health/live` (process up) and `GET /health/ready` (200 only when `SELECT 1` on the app's pool and `GetQueueAttributes` on the input queue both answer within 2 s; 503 with `{ ready, postgres, sqs }` otherwise). The compose healthcheck and nginx's `depends_on` use readiness, so an instance that cannot reach Postgres or SQS leaves the load balancer.

## How the tests prove the guarantees

Real PostgreSQL and real LocalStack SQS everywhere below the unit layer; no mocks of either. Each test file owns a database and its queues. After every integration and e2e test, `expectMoneyInvariants` checks the whole database: `balance == SUM(ledger)` per wallet, `version == 1 + non-OPENING entries`, one `WalletBalanceChanged` per ledger entry, one status event per decided transaction.

Mapping to spec section 13 (concurrency, real parallelism):

| Item | Where |
|---|---|
| 1. Same bet 50 times in parallel, one debit | `test/concurrency/wallet-concurrency.test.ts` (3 instances), `test/e2e/multi-instance.e2e.ts` (3 replicas) |
| 2. Two 80.00 bets on 100.00 | both files; the test parks both requests on a `FOR SHARE` lock and releases, so the worst interleaving is guaranteed |
| 3. Different wallets in parallel | both files, plus "one wallet locked, another served" |
| 4. Three or more instances | concurrency suite (3 pools in one process), e2e (3 containers behind nginx) |
| 5. Worker dies after commit, before ack | `sqs-consumer.test.ts` (handle without delete, visibility forced to 0, redelivery recognised by the inbox); e2e SIGKILL of a replica with requests inside their transactions |
| 6. Two publishers on one outbox | `outbox-publisher.test.ts` (2 apps, 140 events, 140 distinct ids, per-wallet order; death after publish before commit); e2e: every outbox event of the run delivered to `wager-events.fifo`, 0 duplicates by `eventId` (926 events in the recorded run) |
| 7. ROLLBACK/REFUND before the reference | `pending-reference-worker.test.ts` (REFUND, ROLLBACK and WIN before the BET, backoff, cap, TTL, two workers racing); e2e |
| 8. Restart with final consistency | e2e: SIGKILL and `docker compose restart app` under load, invariants and outbox drained afterwards |

Every slice was closed with **mutation testing**: I planted the defect the test exists to catch and required the test to go red, then restored the code. Mutants killed include: wallet lock removed (two 80.00 bets answer `[200, 503]` through the version guard; lock and guard both removed produce a real double debit caught by the invariant); `FOR UPDATE` instead of `FOR NO KEY UPDATE` (deadlock `40P01`); unique indexes dropped (several copies of one bet debit until the balance is gone); ack before commit; inbox insert removed; `SendMessage` inside `enqueue` (an event published for a rolled-back transaction); `SKIP LOCKED` removed from the outbox claim and from the worker claim; the `NOT EXISTS` per-wallet predicate removed (out-of-order within a group); attempts cap and TTL removed; "already reversed" re-check removed (second credit blocked only by the index, as a 500); `OFFSET` pagination (duplicates while bets commit); two-statement reconciliation (false divergence); redaction removed; `55P03` not translated; outbox pause on every short batch (10.05 s instead of under 1.2 s). Two mutants survived on purpose and are documented: moving the idempotency insert after the lock (the unique index still protects money; insert-first is throughput) and dropping `ck_ledger_direction` (`ck_ledger_balanced` fires first in alphabetical order; the direction CHECK stays as the readable statement of the rule).

## Limitations and what I would do in production

- **Authentication** is a no-op guard. Production: Keycloak client-credentials as described above.
- **Per-wallet outbox head-of-line**: an event in backoff holds later events of the same wallet; other wallets are unaffected. Acceptable here because the backoff only happens when SQS itself is down. For higher volume I would batch all pending events of one aggregate in order per round and use `SendMessageBatch`.
- **Pending-reference TTL**: 12 attempts / 24 h are defaults, not measured against a provider's real delays. I would make the base delay and cap configurable too, and trigger the worker immediately when the referenced BET lands instead of waiting for the tick.
- **Replay vs 409 on a simultaneous duplicate** depends on which unique index Postgres reports first (today the key index, created first). I would resolve the loser by looking the row up by `(providerId, externalTransactionId)` and comparing key and hash, removing the dependency on index order.
- **Ledger chaining** (`balance_before` of an entry equals the previous `balance_after`) is checked by the test invariant, not by the schema. A trigger could enforce it; the reconciliation could also verify the chain.
- **Reconciliation** sums the whole ledger of a wallet per call. A periodic checkpoint table would bound the cost for old wallets; a scheduled job would reconcile all wallets, not only on demand.
- **DLQ double copy** (interpretation 13) is possible if `DeleteMessage` fails right after the explicit dead-letter send. Setting the consumer's explicit threshold to one delivery before the redrive policy removes it.
- **Shutdown** waits for the current long poll (up to 20 s) because an aborted poll leaves a ghost message on LocalStack; I have not verified AWS behaves the same. In production I would measure it and either abort or shorten the wait.
- **Logs**: money inside error message strings or nested deeper than three levels is not redacted; `safeReason` covers the known case (driver messages). A log sink with its own PII rules would be the second layer.
- **Test isolation across checkouts**: database and queue names are fixed per test file, so two checkouts running the suite against one Postgres collide. A namespace suffix per checkout fixes it.
- **No load test** (`bun run test:load` is not provided). The outbox drain measurement (20 events, 10.05 s to under 1.2 s) is the only throughput number in this repository.
- **Operational**: no OpenTelemetry traces, no process metrics, no dashboards, no `AWS_ENDPOINT` unset path (the SQS client always receives an endpoint, LocalStack by default).

## How I worked with AI agents

I designed the system and made the decisions in this document: the layering, the single-transaction order of statements, insert-first idempotency, the lock flavour, the inbox/outbox contracts, the failure taxonomy, the test strategy (real infrastructure, forced interleavings, mutation per slice). Implementation was done by coding agents working in parallel git worktrees, one slice each (domain, schema, money path, consumer, outbox, pending-reference worker, queries, observability, multi-instance), each with a brief that fixed the behaviour, the tests that had to exist and the mutants that had to die. Each slice came back with a report: what was built, which tests prove it, which mutants were killed, and the decisions the brief did not cover, listed as options with trade-offs for me to pick. A separate adversarial review pass read the whole codebase against the spec and probed the running service; its findings (FAILED replay answering 500, outbox throughput cap, lifecycle hook order, impossible references waiting out the TTL, driver messages in logs) were fixed in a final slice with their own red-then-green tests. I reviewed the diffs and the decision tables, resolved the open options, and wrote this document from them.
